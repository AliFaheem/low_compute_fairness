# Roman Urdu transliteration: prompts and settings

How the Roman Urdu split (`data/our_data/roman_ur/`) was produced from the Urdu PakBBQ split. Generated by `scripts/transliteration_to_ru/transliterate_roman_urdu.py`, run 24–25 October 2026.

## Model and settings

| Setting | Value |
|---|---|
| Model | `gemini-3.5-flash-lite`, on Vertex AI (location `global`) |
| Temperature | 0.7, so that spelling in context and questions varies naturally, as in real Roman Urdu |
| Output format | JSON mode with a schema: the 5 string fields `context`, `question`, `ans0`, `ans1`, `ans2` |
| Safety filters | `BLOCK_NONE`, because PakBBQ items describe stereotypes and default filters can block benign items |
| System prompt | `roman_urdu_transliteration.txt` (current, v2) |
| User turn | The item's 5 Urdu text fields as a JSON object |
| Max attempts per item | 6 (1 + 5 retries) |

Only the 5 text fields are sent and replaced. All other fields (`id`, `label`, `answer_info`, metadata) are copied unchanged from the Urdu item.

## Post-processing and validation

1. **Non-Latin words.** Roman Urdu text should contain only Latin letters a–z/A–Z, digits and punctuation. The model sometimes leaves a word, or part of one, in Urdu or Devanagari script (e.g. `saalہ`, `nam معلوم`); this happened in about 8% of items.
   - **First 544 `Age.jsonl` items** (IDs in `roman_urdu_retry_phase_item_ids.json`): such outputs were rejected and the item retried, with this text appended to the user turn: "Your previous answer was rejected: non-Latin script in `<field>` (`<characters>`). Every word must be in Latin letters." For the first ~200 items the retry came after a short backoff; after that it was immediate.
   - **All other items:** such outputs are accepted. The item and its offending words are recorded in `data/our_data/_build/roman_ur/needs_cleanup.log`. A later cleanup pass replaces only those words.
   - **Cleanup:** after the run, every distinct leftover word was listed with its context. Replacements were drafted and then reviewed by a team member; the reviewed list is `roman_urdu_word_fixes.csv`. They were applied as whole-word replacements: 142 distinct words, 1,178 occurrences. No non-Latin words remain.
   - **Phrase fixes:** 4 hand-added phrase rows in the same sheet fixed errors written in Latin letters (25 occurrences):
     - `Islamabad terutama` → `Islamabadi` (12 items): the model replaced اسلام آبادی with the city name plus the Indonesian word *terutama*;
     - fragments left before corrected words: `um ummeedwaron`, `sh shirkat`, `mehs mehsoos`.

     The Latin-only check cannot detect errors like these.

2. **Consistent answer options.** The first Roman spelling produced for a given Urdu answer string is stored in `data/our_data/_build/roman_ur/answer_cache.json`. It is reused for every later occurrence, so an option such as نامعلوم ("Unknown") reads `namaloom` in every item. A spelling that contains non-Latin words is never cached, and such an answer is replaced by the cached spelling when one exists. Context and question are not normalised and keep their natural variation.

3. **Bounded retries.** API errors (rate limits, server errors, timeouts, unusable responses) are retried at most 5 times per item. An item that still fails is logged to `failures.log` (in `data/our_data/_build/roman_ur/`) and retried on later runs, at most 3 runs in total. A run stops if 10 items in a row fail.

4. **Structure check.** `scripts/data_prep/validate_splits.py` confirms the split matches `en`/`ur`: same files, IDs, order, keys, labels and metadata.

## Prompt versions

| Version | File | Items |
|---|---|---|
| v1 | `roman_urdu_transliteration_v1.txt` | First 140 items of `Age.jsonl`; IDs in `roman_urdu_v1_item_ids.json` |
| v2 | `roman_urdu_transliteration.txt` | All other items |

v2 adds an explicit rule to convert every word, including common ones, and to use no Urdu or Devanagari characters. It also adds one worked example and a self-check instruction. The change was made because about 1 in 12 v1 first attempts left Urdu script in the output: half-converted words such as `nam معلوم`, or untouched common words. All v1 items passed the same Latin-only check.

## Known limitations

- The source Urdu answer option for the group "Muhajir" is مہاجرین ("refugees"), a translation error in PakBBQ. It is transliterated faithfully as `Muhajreen`, while contexts say `Muhajir`.
- Transliteration is automatic. Occasional wrong spellings occur (e.g. `mustard` for مسترد, "rejected"). A native-speaker check of a stratified sample is planned.

# Evaluation prompt (all languages)

`pakbbq_eval_prompts.json` holds the prompt text used to evaluate models on PakBBQ, one entry per split (`en`, `ur`, `roman_ur`).

## Source

- `en` and `ur` are copied verbatim from the PakBBQ authors' code: the instruction from `GPT_and_DeepSeek_eval.py/streamline_batch_pipeline.py`, the layout from `Gemini_eval.py/create_jsonl.py`.
- `roman_ur` is our transliteration of the Urdu prompt. Spellings follow the most frequent forms in our Roman Urdu split (e.g. `aik`, `sawalat`, `mutabiq`, `baghair`, `tehreer`).
- Roman Urdu uses the labels A/B/C: there is no Latin form of ا/ب/پ, and Roman Urdu users write A/B/C.

## Layout

We use the authors' Gemini layout: one plain-text block, instruction first, no system/user split. This suits base models, which have no chat template.

```
{instruction}
{context}: <item context>

{question}: <item question>

{options}:
{label0}. <option>
{label1}. <option>
{label2}. <option>

{respond}
{answer_cue}
```

## Changes from the authors' prompt

- `answer_cue` (`Answer:` / `جواب:` / `Jawab:`) is added as the last line. Base models need it so that the next token is the answer label. The model is scored on the probability of the 3 label tokens at that position, not on generated text.
- The Urdu `respond` line ends in `۔`, as in the GPT pipeline. The Gemini pipeline ended it with a Latin `.`.
- The options are shown in 3 cyclic orders. The authors used one order.
